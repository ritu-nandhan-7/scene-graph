# Phase B2 — CLIP Visual Encoder Browser Feasibility

**Date:** October 20, 2026
**Final classification:** **BROWSER INFERENCE VERIFIED WITH LIMITATIONS**
**Scope:** Isolated `experiments/browser-feasibility` export and browser test only. No production frontend, backend, checkpoint, OpenCLIP cache, or original source module was changed.

## Decision

The exact production OpenCLIP image-encoding behavior was exported as an FP32 visual-only ONNX graph and executed in a real Chrome browser with ONNX Runtime Web. This is a model-execution result: Chrome completed `InferenceSession.create()` and `session.run()` using identical saved Python preprocessed input tensors, producing raw `[N,512]` features with close numerical parity to Python.

The material limitation is performance and download/init size, not operator support. The visual-only model is 351,780,080 bytes (335.48 MiB). In Chrome 155 with deliberately one-thread WASM, a 68-crop batch required 32,744.4 ms in one `session.run()`; 100 crops required 45,770.6 ms. Thus browser-only execution is technically possible but not currently interactive for a typical 68-pair scene graph under WASM.

## 1. Exact production behavior inspected

Active production wrapper: `notebook/models/relationship/encoder.py`.

| Item | Verified behavior |
|---|---|
| Library | `open_clip` / `open_clip_torch` 3.3.0 |
| Model | `ViT-B-32` |
| Weights selector | `pretrained="openai"` |
| Local artifact | existing Hugging Face OpenCLIP cache (`timm/vit_base_patch32_clip_224.openai`) |
| Runtime call | `self.model.encode_image(images)` |
| Evaluation | `model.eval()`, gradients disabled |
| Output | `features.float()`, raw 512-D float32 feature |
| Post-output L2 normalization | **none** |
| Tokenization | none: only the visual tower is used by the relationship pipeline |

The emitted transform representation from the active local loader was:

```text
Resize(size=224, interpolation=bicubic, antialias=True)
CenterCrop(size=(224, 224))
MaybeConvertMode() -> RGB
MaybeToTensor()
Normalize(mean=(0.48145466, 0.4578275, 0.40821073),
          std=(0.26862954, 0.26130258, 0.27577711))
```

The upstream pair feature path was also inspected. Each directed pair builds an expanded (`0.20`) union crop, using the exact Python rounded/clamped crop bounds; it passes that RGB crop through the transform above and sends the **unnormalized embedding** to the relationship classifier. Crop geometry and pixel-crop rounding remain separate behavior.

## 2. ONNX export

Generated by the isolated `run_b2_b3_clip_relationship_export.py` script:

```python
class VisualOnly(torch.nn.Module):
    def __init__(self, clip_model):
        super().__init__()
        self.visual = clip_model.visual

    def forward(self, image):
        return self.visual(image).float()
```

The export used FP32, opset 17, `do_constant_folding=True`, and dynamic batch axes:

```text
image          float32 [N, 3, 224, 224]
image_features float32 [N, 512]
```

PyTorch's evaluation fast path initially emitted `aten::_native_multi_head_attention`, which is not an ONNX operator. The isolated exporter disabled that **PyTorch export-time MHA fast path only** so equivalent attention math lowered to standard ONNX matrix/softmax operations. This did not alter weights, preprocessing, output normalization, production source, or cache files.

## 5. Preprocessing parity boundary

The browser test intentionally used saved Python-preprocessed tensors for runtime parity. It did **not** claim that browser Canvas processing is identical to OpenCLIP/Pillow bicubic resize plus center crop. The browser implementation must preserve:

1. pair-specific expanded union crop (`20%` per input box);
2. Python ties-to-even `round()` for clamped crop bounds, not JavaScript `Math.round()`;
3. RGB conversion;
4. shortest-side resize / bicubic interpolation / center crop to 224;
5. exact CLIP mean/std; and
6. no post-encoder L2 normalization.

That browser crop/resample parity is still open. It is deliberately separated from the verified browser runtime result.
